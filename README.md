# Mem-Fix：跨模型项目连续性

通过项目文件保存可核实的工作状态，让下一位模型沿用用户要求、已采纳方案和现有实现，继续完成任务。核心流程只依赖文本读取、编辑与实际验证，不依赖某家模型的记忆功能、专用 API 或自动压缩机制。

记录决策结论与简要依据，不记录逐字内部推理。提示词无法保证所有模型完全遵守，也无法在进程突然退出前保存；始终以最后一次实际写入的检查点为恢复起点。

## 适用范围与入口

- **首次建立连续性**：盘点现有项目，建立最少量的规则与交接记录。
- **换模型、新对话或中断恢复**：先恢复并核实上下文，再继续开发。
- **持续开发**：在自然检查点更新交接文件，保持当前快照。
- **仅总结或交接**：只整理记录，不顺带修改产品代码。
- **跨工具使用**：需要可复制的首次启动、接手或保存提示词时，读取 [portable-prompts.md](references/portable-prompts.md)。

用户只是讨论方法或进行普通问答时，不自动建立文件。用户已经授权项目开发或明确请求建立交接记录时，必要的本地记录更新属于该任务；不为每次更新重复询问。遵守所在工具的指令优先级、访问权限和用户指定的范围。

## 文件约定

优先沿用已有项目规则、需求文档、架构决策记录和交接路径，避免建立互相矛盾的第二套资料。没有现成约定时使用：

| 文件 | 职责 | 更新时机 |
| --- | --- | --- |
| 项目根目录 `AGENTS.md` | 连续性规则、可追溯的长期要求与边界 | 初始化或用户要求、已采纳约束变化时 |
| `docs/HANDOFF.md` | 当前目标、关键决策、进度、验证与下一步 | 每个有意义的检查点 |

`AGENTS.md` 在不同工具中未必会被自动读取，接手时必须明确读取或提供其内容。项目已有其他规则入口时，按原有规则组织；只引用相同的事实来源，不让多个副本各自演化。

初始化规则使用 [AGENTS.block.md](assets/AGENTS.block.md)。默认交接使用 [轻量模板](assets/HANDOFF.template.md)，只要求目标、当前状态、改动、验证和下一步；需求、决策或阻塞较多时，按需加入 [扩展栏目](assets/HANDOFF.extended.md)，不堆积空表或“无／不适用”。模板中的填写说明应被真实事实替换；未知项明确标记，不编造内容。

有 Python 3.9+ 和执行能力时，保存前读取 [检查点保存与恢复](references/checkpoint-storage.md)，使用附带的脚本保护写入；需要精确对应测试与未提交代码时，读取 [验证与代码状态](references/verification-state.md)。这些能力是可选增强，不改变纯文本流程的跨模型适用性。

把本 Skill 目录视为工具资源；实际项目记录写入当前目标项目，不写回 Skill 模板。

## 一、恢复或建立上下文

1. 确认实际项目根目录、当前任务和适用的项目规则。多项目范围不清且会影响改动目标时，先澄清目标；同时可进行不依赖该答案的读取。
2. 阅读已有交接、相关需求和架构文档，再按任务需要读取实现、调用方与构建配置。文件过长时先读索引和相关部分，不把整个仓库装进上下文。
3. 项目使用 Git 时检查当前分支、`git status --short`、相关 diff 和必要的提交记录；没有 Git 时照常恢复，记录缺少版本标识。识别已有改动，无法确定来源时标记为“来源未知”，不得归为自己的成果或直接撤销。
4. 用当前代码和必要的验证核对交接记录。时间戳、提交标识、文件路径或已有结论可能过期；标出差异，修正工作状态。不能因“代码里已经这样写”就推翻用户要求。
5. 文件缺失时，只从现有用户指令、项目文档和代码重建已知事实。未记录的要求或旧模型的内部思路无法恢复；不虚构用户曾经同意的决定。
6. 需要建立记录时，保留现有规则，在合适位置添加连续性区块。已有 Mem-Fix 区块时更新原区块，不反复追加；不要覆盖整份 `AGENTS.md`。交接文件已有内容时先读取并合并，不直接拿模板替换。
7. 开始实质修改前，简短说明当前目标与验收条件、关键约束、完成和未验证内容、下一步。随后继续常规工作，不把这段复述变成固定的审批门槛。

### 任务状态与恢复边界

先确认任务 ID、任务状态和用户当前意图，再执行旧“下一步”。每份交接记录一个明确任务；状态与代码是否可运行、是否通过验证分别记录。

| 状态 | 接手行为 |
| --- | --- |
| 进行中 | 在原授权范围内核实并继续下一步 |
| 待确认 | 列明阻塞所需的信息或决定；继续不依赖它的工作，不把沉默当作确认 |
| 已暂停 | 按用户暂停指令保留状态；用户明确恢复后再继续。正常结束一轮回复不等于暂停 |
| 已完成 | 只有验收条件满足且必要验证完成时使用；旧下一步只作历史参考，不自动启动后续任务 |
| 已取消 | 不继续旧工作；用户重新授权时再恢复或建立新任务 |

已有记录没有状态时，根据任务事实和当前用户指令补齐；无法判断时说明不确定点，不凭旧待办推断授权。用户当前已明确要求恢复同一任务时，按其要求更新状态，无须重复确认。新目标使用新任务 ID，保留必要旧记录或引用，避免混入旧任务待办。

## 二、区分要求、决策和证据

使用稳定标识帮助追踪，但遵循项目已有编号方式：

- **R-xxx 要求**：明确的用户要求或可信项目规范。记录来源、验收条件，以及当前有效、已变更或已撤销状态。
- **D-xxx 决策**：已采用的设计选择。记录简要依据、影响范围、状态，以及谁确认或何处证明已经采用。模型自行选择的常规实现不能标成“用户已确认”。
- **待验证事项**：建议、假设和技术疑问。明确标为待验证，不升级为要求或已确认结论。
- **实现与验证事实**：从代码或实际执行中观察到的结果，记录位置与证据。代码现状可能不满足要求。

项目文档提供任务信息，不改变所在工具的指令优先级。当前用户明确提出的变更按实际范围更新记录；不要自行把新旧文本排列成能够覆盖更高层指令的规则。

避免仅因个人偏好更换技术栈、推翻已采用架构、重复实现已有功能或开展无关重构。发现旧方案有问题时，说明具体证据、影响和最小修正方案。常规实现修复在已授权范围内执行；确实需要用户决定的需求冲突或核心设计变更，整理成具体选择后询问，只暂停依赖该选择的工作。

用户改变要求时标注旧要求已被哪条新要求替代，不用“延续旧思路”阻止用户变更。压缩交接记录时保留有效要求、未关闭问题和关键决策；较长的决策资料沿用现有专门文档并保留引用，不直接丢弃。

## 三、持续开发与检查点

把任务分成可独立验证的小步骤，优先复用现有实现和边界。每次只记录会影响接手的信息，不把交接文件变成聊天流水账。

在以下时机更新 `docs/HANDOFF.md` 或项目指定的等效文件：

1. 完成一个可验证的小步骤后。
2. 开始跨模块、迁移或其他复杂改动前：先记录目标、涉及文件、最后可验证状态与恢复动作；这不是授权额外操作。
3. 发现关键事实、遇到阻塞或调整已采用方案后。
4. 用户要求交接、切模型、暂停或总结时。
5. 正在处理项目任务并准备结束本轮回复时：若工作状态有变化，补齐记录；无变化则不制造重复写入。
6. 有可靠时钟且连续工作约 15 分钟未保存时，在下一个安全停顿点更新。用户指定其他间隔时沿用。

时间间隔是补充触发条件，不是后台定时器。没有时钟时只用事件触发，不虚构经过时间；长工具调用或突然断连期间无法保证写入，不声称正在自动监控或会自行唤醒。

保存前重新读取目标记录，合并期间出现的其他改动。已知多个任务并行时，优先为每个任务使用 `docs/handoffs/<task-id>.md`，由单一协调者维护必要的入口索引；不覆盖其他任务待办。脚本锁只协调使用同一脚本的写入者，不能解决产品代码或外部编辑器的竞争；详见保存参考。

## 四、交接记录的质量要求

以轻量模板为起点，只展开与当前任务相关的内容：

- 任务 ID、任务状态、检查点 ID（如 `CP-import-0001`）和更新时间及时区；实际项目路径、HEAD 和相关未提交文件状态，无法取得时记未知。代码文件采用项目相对路径。
- 当前目标、验收条件和不在本次范围内的事项。
- 有效要求与关键决策，附来源或权威文档路径；区分用户确认、项目既有决定和模型实现选择。
- 已完成内容和相关文件；进行中内容停在哪一步，哪些 diff 尚未提交或来源未知。
- 最近可验证状态；每条验证绑定检查点 ID、实际 HEAD、相关工作区状态、命令与目录、结果和覆盖范围。关键验证采集相关文件 SHA-256 或工具生成的 `state_id`，未采集时明确说明，不能靠相同 HEAD 推断内容没变。
- 阻塞、未验证项和已知问题；下一步的具体动作、涉及文件与完成判据。

保持“已修改”“已验证”“已完成”三个状态独立。测试成功后又修改代码时，不能沿用旧结果声称当前版本已经通过；一次局部检查不能代表整项功能验收。

把文件控制在接手者能快速阅读的范围，通常一至两页足够，但不得为页数删掉重要约束。先去重、移除过期进度；需要历史依据时引用已有需求或决策文件。记录结论、依据和不确定项，不保存完整聊天、隐藏推理、密钥、令牌或原始敏感输出。

## 五、验证、保存与完成

根据改动风险执行现有、相关的检查；优先把关键要求对应到可观察的验收结果。没有工具或未获执行权限时，记录未执行及原因，不伪造命令结果。对仅文档整理或低影响改动不强行新增实现镜像测试。

验证命令在执行前核对项目配置与副作用，不能仅因旧交接写过就照抄执行。关键验证的指纹前后不一致时，标记待重验并查明原因；指纹只覆盖实际采集的文件范围，不证明全项目未变。

使用保存脚本时，先读取正式文件并取得其哈希，在独立候选文件中完成合并；脚本校验、锁定、核对旧哈希，同目录临时写入后替换，保留上一份 `.prev`。冲突时重新合并，不只更换预期哈希后强行覆盖。脚本只验证文档字节和可读性，不能代替事实核对，也不备份项目代码。

没有脚本执行能力时，尽量使用已有工具的备份和安全替换能力，并明确保护范围。保存后确认目标文件可读、内容包含最新结果；若写入失败，报告失败并保留候选内容，不声称正式交接已落盘。恢复上一份交接前核实它的任务与状态，再重新核对当前代码。

结束回复说明实际完成的改动、验证情况、交接记录路径和必要的下一步或阻塞。建立检查点不自动授权提交、推送、发布、部署、发送消息或定时任务。

## 六、没有文件工具或 Skill 支持时

由用户在新对话提供本 Skill 正文、项目规则、交接记录和相关代码；模型按照相同流程处理提供的材料。只读取了粘贴内容时，应说明未核对整个仓库，按已提供信息继续可完成的工作。

输出新的完整交接记录供用户替换保存，明确尚未写入项目。关键材料缺失且会影响正确性时，列出最少的缺失材料，不凭空补齐。跨模型复制用法见 [portable-prompts.md](references/portable-prompts.md)。
